# ✅ 天R 登入器 B4：中繼補發 S_KEY 與進入世界實證（2026-10-30）

> [!IMPORTANT]
> **一句話結論**：登入器 B4（`inject_s_key=true`）在客戶端連入中繼後**自行補發 13 bytes 的 S_KEY（opcode 15）**，客戶端立刻恢復送包；中繼把 opcode 199 改寫成 17 bytes 明文帳密包後**服務端接受登入**，21:17:09 回 `opcode 234`＋公告；21:17:50 出現選角畫面（6 格）、21:17:56 選角確認後進入批次載入，**21:20 進入世界並可自由操作**（開背包、開世界地圖、與 NPC 對話、開商店、持續移動）。

## 2. 本次程式改動（登入器側）

### 2.1 `relay.rs`

```rust

// （實測 36～168 秒上下行 0 bytes 後自行關線）。中繼在客戶端連入後補發同一幀。

    0x0D, 0x00, 0x0F, 0x42, 0x90, 0xE1, 0x7A, 0xA4, 0x29, 0x70, 0x53, 0x00, 0x00,
```

  `iw.write_all(&S_KEY_FRAME)`（只寫往**客戶端**方向，服務端完全不知情）。
- 幀內容取自 2026-10-28 真實伺服端 S_KEY：`0D 00 0F 42 90 E1 7A A4 29 70 53 00 00`
  （`key=0x7AE19042`、`key2=0x537029A4`，見 [[20261024-天R客戶端BIN反編譯與主體脫殼]] §10.20）。

## 4. 對照：為什麼 21:00 那次失敗、21:17 這次成功

| 變因 | 21:00（B3，`inject_s_key` 不存在） | 21:17（B4，`inject_s_key=true`） |
| :--- | :--- | :--- |
| S_KEY 是否送達客戶端 | ❌ 無（服務端依 ADR-005 停發） | ✅ 中繼補發 13B |
| 客戶端行為 | 連上後 **0 bytes**，100～168 秒後自行關線，UI 停在龍圖 | 第 3 秒即送 161B，第 10 秒送 295B |
| 登入結果 | 無 | `測試1` 進入遊戲、`玩家=1` |

**結論（observed）**：S_KEY 對客戶端是**送包觸發器**，不是「加密開關」——本次全程明文可解析（161B body 為可讀 protobuf、194B 公告為可讀 Big5），證實客戶端全域加密旗標 `0x145EAA9CC` 仍為 0（八刀未動它）。

**推論（inferred，未驗證）**：opcode 199 的 288B body 高熵與「加密旗標」無關，較可能是 protobuf 內含雜湊／MAC／一次性 token 等二進位欄位；本次以 17B 明文 `account\0password\0` 取代即被接受，因此**不需要**解出原 body 格式。
