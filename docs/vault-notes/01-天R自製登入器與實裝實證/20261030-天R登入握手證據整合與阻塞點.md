## 3. 封包級解析（本輪新增，證據等級 `PASS`）

### 3.1 161B：opcode 244 的明文 protobuf，已完整解出

線上框（2026-10-30 01:33:52 實錄）：

```text
A1 00 | 01 00 00 00 | F4 | 34 03 | 96 00 | protobuf(150B)
總長161   序號=1      op244  子碼=820  長度=150
```

- `A1 00`：總長 161（小端，含自己 2 bytes）。
- `01 00 00 00`：4-byte 序號，**明文**、每條連線從 1 起算。
- `F4`：opcode 244（`C_EXTENDED_PROTOBUF` 容器）。
- `34 03`：容器子 opcode `0x0334 = 820`。
- `96 00`：後續 protobuf 長度 150。
- protobuf 欄位（實測值）：

| 欄位 | 型別 | 值 | 判讀 |
| :---: | :--- | ---: | :--- |
| 1 | varint | 52 | 未定（版本群組／語系？） |
| 2 | varint | 950 | 未定（協議版本？） |
| 3 | varint | 1,284,362,033 | 未定（雜湊／build id？） |
| 4 | varint | **2,002,122,605** | **＝客戶端版本 2002122605**（與 `lin.log` 首行一致） |
| 5 | varint | 1 | 未定 |
| 6 | bytes | 128 B 隨機值 | 挑戰值／nonce（每次連線不同） |

⇒ 161B **是明文**，不是密文；`lin.log` 的 `client version 2002122605` 與欄位 4 完全吻合，可作為解碼正確性的自證。

### 3.2 295B：opcode 199，body 不是帳密明文、也不是已知 CBC 密文

線上框（同日 01:33:59 實錄）：

```text
27 01 | 02 00 00 00 | C7 | body(288B)
總長295   序號=2      op199
```

body 結構（以偏移標示）：

| 偏移 | 內容 | 備註 |
| ---: | :--- | :--- |
| 0–255 | 256 bytes 高熵資料 | 256 個位元組中 162 種不同值，統計上與隨機／密文一致 |
| 256–259 | `DD 0A 68 AB` | 未定（checksum／session id？） |
| 260–263 | `7F 00 00 01` | **明文 127.0.0.1**（伺服器 IP？） |
| 264–267 | `7F 00 00 01` | **明文 127.0.0.1**（客戶端 IP？） |
| 268–283 | `00 × 16` | 16 bytes 全零（token／保留欄？） |
| 284–287 | `0D 00 00 00` | 明文 13（語言／server id／長度？未定） |

**三條硬證據，直接推翻「199 body 全密文」的舊結論**：

1. **序號是明文且遞增**：161B 是 `01 00 00 00`、295B 是 `02 00 00 00`。若整段載荷走 `buf[i] ^= buf[i-1] ^ db[i&7]` 的 CBC 鏈，序號不可能還是乾淨的 1、2。⇒ 舊筆記「CBC＋序號全密文」的說法不成立。
2. **尾端 28 bytes 是結構化明文**：兩個 `7F 00 00 01`、16 個零、一個 `0D 00 00 00`。全密文不可能留下這種可辨識結構。
3. **用伺服端真演算法解密失敗**：以 `LineageEncryption.initKeys(0x7AE19042L)`（真 seed，來自實錄 `42 90 E1 7A`）得到 `db = 8A 36 DF 2B FB 08 A2 C4`，對 161B／295B 做 6 種變體（完整載荷各自、鏈式 161→295、opcode 起各自）**全部輸出不可讀垃圾**，沒有任何帳號字串或 protobuf 結構。

⇒ 199 的 body 格式目前是 `OPEN`：可能是自訂二進位、特定欄位加密（例如只加密前 256B 的帳密塊）、或以另一把金鑰（非 KeyPacket seed）做的密文。**在格式解出前，不應再把它描述成「CBC 全密文」。**

| 舊說法 | 現況 | 依據 |
| :--- | :--- | :--- |

## 5. 兩個硬矛盾（需要決策，不是再試一次就能繞過）

### 5.1 S_KEY 是「送包前提」 vs ADR-005「永久停發」

- 客戶端沒有 S_KEY → 不送任何資料（兩次獨立實測：2026-10-24 中繼吞包、2026-10-30 伺服器不發）。
- ADR-005 明訂「永久停發 KeyPacket、雙端明文、任何代理人不得重新啟用」。
- ⇒ **目前 ADR-005 的實作方式（完全不發）等於讓客戶端永遠不進入登入流程。** 這不是「再調一個參數」能解的問題，而是「要不要保留 S_KEY 作為觸發、以及由誰吸收它帶來的加密狀態」的架構決策。

### 5.2 199 body 不是 `C_AuthLogin` 的帳密佈局

- 伺服端 `C_AuthLogin` 從 `_off = 1` 起用 `readS`（NUL 結尾、BIG5）讀帳號（2–14）與密碼（4–16）。
- 實際 199 body：288 B、開頭 256 B 高熵、尾端結構化明文、**沒有早期 NUL、沒有 ASCII／BIG5 帳號**。
- ⇒ 「不合法帳號長度」是**佈局不符的必然結果**；即使把 S_KEY 拿掉或把 body 解密，只要 199 的真實格式沒解出，`C_AuthLogin` 還是讀不到帳密。

> 附帶：`C_AuthLogin` 印的 `127.0.0.1` 是 `client.getIp()`，不是帳號；這行 log 會誤導除錯，已在前篇記錄。

## 7. 下一步探針（具體、可重現）

1. **A 實驗（最優先）**：在 `127.0.0.1:2000` 起一個假登入伺服器，客戶端連上後送一個非 15 的首包（先試 `240/821` 版本包，再試任意 `opcode=1` 的 13B 框），觀察是否收到 161B。
   - 判準：假伺服器讀到 > 0 bytes（尤其 `A1 00 01 00 00 00 F4`）。
   - 注意：同一 IP 2 秒內第二條連線會被 `ConnectionThrottleFilter(2000L)` 關掉；一次只開一條。
2. **若 A 失敗**：用 `dump_Lin.img` 核對「客戶端在 `0x0F` handler 之外是否還有其他送包觸發點」，特別是 `0x1409E4BD0` 的 handler 是否同時負責設定 UI 狀態／喚醒 `isfd()`。
3. **199 body 格式**：以 01:33 的完整 288B 為樣本，依序測試：
   - 256B 區塊的 Blowfish-ECB／CBC（key 用 `getSeeds` 派生值或原始 seed）；
   - AES-128/256（key/IV 可能來自 161B 的 128B blob）；
   - 尾端 32B 的結構來源（`DD0A68AB`、兩個 IP、16 零、13）。
4. **只有在 A 成立且 199 佈局解出後**，才討論改伺服端（B）或中繼（C）；任何涉及重新啟用 S_KEY 的改動，都必須先走獨立 ADR，不得直接改 `LineageProtocolHandler`。

### 後續固定流程

1. **決策與版本閘門**：不改 ADR-005、不重啟 KeyPacket；每次探針先記錄 source/JAR 指紋，執行 I:/RHD/checks/verify-keypacket-stopped.ps1 -ServerRoot X:/L1RHD/L1RHDserver，保存 GateA、GateB 與 JAR SHA。正式 launcher.json 保持 inproc_launch=false。
2. **隔離設定**：建立唯一一次性 profile，packet_capture=false，relay 與假伺服器使用隔離 port；不重用已消耗 marker。不要預先綁定 fake backend port 3001。
3. **以實際 relay 事件開閘**：先由 B2 日誌等到 [#n] 客戶端連入，再立即綁定 3001；目前證據顯示登入器會在 Lin.bin 建立後、客戶端連入 relay 前再開預連線，所以只檢查 process 存在不算有效判準。若直接在 2000 接客戶端，先確認拓撲不會再被 B2 relay 攔截。
4. **最小封包採證**：v3 已在有效 marker 後送出 90B 240/821，但 C>S 與標頭讀取皆為 0；不得原樣重跑。若採下一個路線 A 候選，先按匹配 hash 的客戶端證據核對 trigger，再使用獨立的一次性隔離 profile；既有手冊列出 raw 1-byte opcode=1、總長 13B 的探索候選；匹配 hash 客戶端報告 §10.12.1 顯示連線狀態 ≠3 時第二張 switch 只接受 7–240，opcode 1 直落共同出口；預登入 runtime state 及 state 3 下的 raw opcode 1 case 尚未確認，因此此候選低信心。protobuf 子 opcode 1 屬不同層，不可互證。v4 profile 已離線預備，live attempt 仍須新的一次性授權。每次仍最多讀 7 bytes，只記錄 frame length、sequence、opcode。讀到 opcode 244 才算路線 A 有效；預連線、connection refused、EOF/0 bytes 或 generic error code [0] 不得記成密碼錯誤。
5. **協議修改閘門**：只有收到實際客戶端的 244 後，才繼續核對 199 格式與 C_AuthLogin 契約；有了可重現證據及使用者架構決策，才另立 ADR 討論服務端解密／handler 或中繼適配器。Java 變更需先備份、先寫正確 seam 的回歸測試、編譯測試、核對部署 JAR 指紋，再做實機驗收；每一步記錄 source、產物與執行中 PID。
