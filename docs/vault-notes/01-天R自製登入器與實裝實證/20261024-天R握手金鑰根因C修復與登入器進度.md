# 天R 握手金鑰根因C修復與自製登入器進度

> **一句話結論**：依 [[20261024-天R客戶端BIN反編譯與主體脫殼]] §10.21.3 的「根因 C」，本機伺服器端確認**發 KeyPacket 但全程明文**，客戶端收到後單向鎖死成加密模式 → 握手成功的瞬間通訊就壞掉。**已套用處方 A（停發 KeyPacket）並實測驗證通過**。

---

## 1. 三端證據鏈（本輪實測）

### 1.1 伺服器端確認：真的在發 KeyPacket

```java
// LineageProtocolHandler.java:19-27（修復前）
public void sessionOpened(final IoSession session) {
    if (!session.isClosing()) {
        final long seed = Config.SeedVal;
        final KeyPacket key = new KeyPacket();
        final LineageClient lc = new LineageClient(session, seed);
        session.write(key);          // 每次連線都送 opcode 15
        session.setAttribute("CLIENT", lc);
    }
}
```

### 1.2 伺服器端確認：encoder/decoder 全程明文

| 檔案 | 實作 | 判定 |
| :--- | :--- | :--- |
| `LineagePacketEncoder.buffer()` | 只前置 2 bytes LE 長度，`buffer.put(data)` 原樣輸出 | **不加密** |
| `LineagePacketDecoder.decode()` | `client.pck.requestWork(data)` 直接丟入 | **不解密、不剝 4-byte 序號** |

### 1.3 伺服器端確認：加密模組是死代碼

`grep LineageEncryption|LineageBlowfish|encrypt_S|initKeys` 於 `src` 全庫：

| 檔案 | 命中數 | 說明 |
| :--- | ---: | :--- |
| `LineageProtocolHandler.java` | 1 | 即 `new KeyPacket()` 那行 |
| `LineageEncryption.java` | 16 | 自身 |
| `LineageBlowfish.java` | 7 | 自身 |

→ **無外部呼叫者，整組加密模組為死代碼**，與筆記 §10.21.3 斷言一致。

### 1.4 LineageClient 的 key 參數完全沒被使用

```java
public LineageClient(final IoSession session, final long key) {   // key 形參
    this.S_TWYX = true;      // 語系修復已生效
    this.C_TWYX = true;
    // ... 函式體內零處使用 key
}
```

### 1.5 KeyPacket 的 key 值與筆記吻合

```java
final int key  = 2061602882;   // 0x7AE2C042 ← 與 §10.21.3 表格一致
final int key2 = 1399859620;
```

## 2. 已套用的修復（處方 A）

### 2.1 修改內容

```java
// LineageProtocolHandler.java:19-33（修復後）
if (!session.isClosing()) {
    final long seed = Config.SeedVal;
    final LineageClient lc = new LineageClient(session, seed);
    // [處方A 2026-10-24] 不停發 KeyPacket。
    // 原因（黑曜石 §10.21.3 根因C）：客戶端收到 opcode 15 後會把

    // 雙端自此錯位 -> 後段封包全亂碼 / Unknown packet。

    session.setAttribute("CLIENT", lc);
}
```

## 3. 自製登入器的技術進度

### 3.1 已實作模組（I:\RHD\RHDLauncher-rs）

| 模組 | 功能 | 狀態 |
| :--- | :--- | :--- |

| `remotehook.rs` | inline hook shellcode 產生 | ⚠️ 已實作未驗證 |

### 3.2 已定位的障礙：module_base 在掛起狀態不可用

`CreateToolhelp32Snapshot(TH32CS_SNAPMODULE, pid)` 對 **CREATE_SUSPENDED 的行程**無法列舉模組，導致 hook 安裝失敗。

**待解方案**（依筆記 §4.1 雙階段架構）：
1. 先 `ResumeThread` 再 hook（有競態風險）
2. 以 `ReadProcessMemory` 直讀 PEB → Ldr → InLoadOrderModuleList
3. 由 `NtQueryInformationProcess` 取 PEB（本機 windows crate 0.61 未 expose，需手動 bind）

### 3.3 重要判斷：hook 可能非必要

依 §10.21.5 第 1 條：「先問對端會不會發 keypacket。發 → 走加密；**不發 → 全程明文**，第 4 步跳過。」

處方 A 已讓伺服器不發，因此客戶端會走明文；而客戶端本來就會連 `127.0.0.1:2000`（見 `LogonX64` 日誌 `正在重定向連接>>127.0.0.1 2000`），中繼已在此監聽。

→ **建議先驗證「停發 KeyPacket + 中繼」是否已足夠，再決定是否投入 hook。**

## 4. 附帶發現（非本輪主線）

### 4.1 readS(boolean YX) 的偏移計算仍是舊寫法

```java
// ClientBasePacket.java:169 —— 與已修好的 readSAt:193 不一致
this._off += s.getBytes(ClientBasePacket.CLIENT_LANGUAGE_CODE).length + 1;
```

**影響評估（實測）**：以 JDK 8 對「測試1／測試角色／龍騎士／阿薩姆／測試ABC」五組做 BIG5↔MS950 往返，長度差全為 0。

→ **純繁體字情境下長度不變，目前不會出錯**。但若字串含 Big5 無法表示的簡體字（轉換後變 `?`），長度會縮水。
全庫有 **47 處**呼叫 `readS(client.C_TWYX)` 走此路徑（含 `C_LoginToServer:101`）。
**列為潛在風險（OPEN），非本次登入失敗之主因。**

### 4.2 編譯環境要點（承接既有紀錄）

- 必須用 **JDK 8**（`jdk-8.0.504.1-hotspot`），JDK 21 會因 `javax.xml.bind` 缺失失敗。
- 單檔編譯若遇 `HBXT` 缺 `claim(String)`／`refund(String,int)`，先編譯來源版 `HBXT.java` 到暫存目錄並排進 classpath（本輪已驗證 exit=0）。
