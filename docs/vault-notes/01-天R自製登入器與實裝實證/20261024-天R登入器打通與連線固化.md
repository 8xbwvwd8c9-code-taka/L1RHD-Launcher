# 天R 登入器打通與連線固化

> **一句話結論**：2026-10-24 19:28 **實測進入遊戲世界成功**（角色 15 級於南邊森林）。
> 本案歷經多輪排查，最終根因是 **DB 角色名編碼與伺服器請求不一致**（繁體 vs 簡體）。
> 連線組合已固化為 `I:\RHD\RHDLauncher-rs\WORKING_SETUP.md` 與一鍵腳本 `Start_Game.bat`。

## 1. 最終可運行組合（7 項必要條件）

| # | 項目 | 正確值 | 錯誤後果 |
| :-- | :--- | :--- | :--- |
| 1 | 伺服器 KeyPacket | **必須發送**（opcode 15） | 停發則客戶端連上後不送任何資料 |
| 2 | Relay 埠 | `2000`、`29467` → `3000` | 不監聽則 `SetConnect [Fail]` |
| 3 | Relay timeout | **須清除**（`settimeout(None)`） | 5 秒後斷線 |
| 4 | `Login.exe` | **原版**（8,679,936 B） | 自製版卡 GameGuard 380 |
| 5 | DB 角色名 | **簡體** `测试1`（`E6B58BE8AF9531`） | 繁體則 `空PC进入游戏被踢` |
| 6 | DB 帳號密碼 | `5566` / `5566` | |
| 7 | `GameGuard` 目錄 | 完整 24 檔，**不可改名** | 380 |

> [!CAUTION] 2026-10-31 改寫（以 ADR-005 固化＋B4 實機為準）
> 上表第 1 項「伺服器 KeyPacket **必須發送**」已過時：現行固化架構＝**伺服端永久停發**（`session.write(new KeyPacket())` 已註解、GateA/GateB 驗證、不得還原）＋**中繼補發 S_KEY 給客戶端**（`inject_s_key=true`，B4 兩次實機進世界、全程明文）。本表的歷史脈絡（2026-10-24 路線 A 時代）保留；最新流程見 [[20261030-天R登入器成功登入流程固化SOP]]。
> 同理 §5「停發 KeyPacket → 客戶端不送資料」描述的仍是**伺服端停發且無人補發**的情境；B4 之後由中繼補發，客戶端恢復送包。

## 2. 根因分析：編碼斷裂（本案最大坑）

### 2.1 症狀

```
資訊: 空PC进入游戏被踢, 账号= 5566 请求角色名= 测试1
```

### 2.2 三端比對

| 位置 | 值 | Hex |
| :--- | :--- | :--- |
| DB `char_name`（修復前） | 測試1（**繁體**） | `E6B8AC E8A9A6 31` |
| 伺服器收到的請求 | 测试1（**簡體**） | `E6B58B E8AF95 31` |
| `L1PcInstance.load()` 查詢 | 繁体名 | → **NULL → kick** |

### 2.3 轉換方向已實測確認

以 JDK 8 實測 `com.spreada.utils.chinese.ZHConverter`：

```
SIMPLIFIED  = 1
TRADITIONAL = 0

輸入 測試1 (E6B8ACE8A9A631)
  mode=0 (TRADITIONAL) → E6B8ACE8A9A631   繁體（不變）
  mode=1 (SIMPLIFIED)  → E6B58BE8AF9531   简体 ✓
```

→ `readS()` 的 `ZHConverter.convert(s, 1)` **確實是繁轉簡，方向正確**。
→ 因此 **DB 必須存簡體**（符合 `run.bat` 註解「ALL internal data is Simplified」）。

### 2.4 修復

```sql
CREATE TABLE characters_backup_20261024 AS SELECT * FROM characters;
UPDATE characters SET char_name='测试1' WHERE HEX(char_name)='E6B8ACE8A9A631';
```

**第一輪（19:38）— 內建 relay 接管**

```
RHDLauncher.exe (pid 21040)
  ├─ relay: 2000/29467 → 3000    ✅
  └─ LogonX64.bin (pid 43348)     ✅

連線：LogonX64(43348) → 2000 → RHDLauncher(21040) → 3000
→ 完全不需要 Python relay
```

**第二輪（19:43）— 完整端到端（最終驗證）**

```
RHDLauncher.exe (pid 30992)
  ├─ relay: 2000/29467 → 3000                          ✅
  └─ Login.exe (pid 34964) → 交接 → LogonX64.bin (4036) ✅

連線：LogonX64(4036) → 2000 → RHDLauncher(30992) → 3000  ✅

Login 日誌：
  wait game Initialize
  game Initialize Complete! Start Exit Login Executes     ← 交接成功
```

> **這是本專案的最終狀態**：使用者只需雙擊 `RHDLauncher.exe`（按 UAC），
> 不需手動開伺服器、不需 Python relay、不需原版登入器 UI。
> RHDLauncher 自動完成中繼、封鎖清單、啟動原版 Login.exe 交接客戶端。

### 4.4 防重複啟動機制

RHDLauncher 於啟動客戶端前會偵測既有 `LogonX64.bin`，若存在則先 `taskkill /F /IM LogonX64.bin /T`，
避免兩份客戶端搶佔 2000 埠造成連線衝突。

## 5.5 實機驗證成功後修正的缺陷（TR-BUG-61）

### 症狀

伺服器日誌出現：

```
十月 24, 2026 7:40:35 下午 com.lineage.server.datatables.CharBuffTable StoreBuff
資訊: 状态保存错误 状态ID==1001 角色ID==536871476
意外角色退出1
```

### 根因

`character_buff` 表主鍵為 **`(char_obj_id, skill_id)` 聯合主鍵**，
但 `CharBuffTable.StoreBuff()` 使用 **`INSERT INTO`**：

```java
pstm = con.prepareStatement("INSERT INTO character_buff SET char_obj_id=?, skill_id=?, ...");
```

同一角色重複保存同一種 buff 時，直接觸發主鍵衝突。手動驗證：

```
ERROR 1062 (23000): Duplicate entry '536871476-1001' for key 'PRIMARY'
```

### 影響

- 登出／斷線時技能狀態無法保存
- 偶發「意外角色退出1」

### 修正

| 項目 | 修改前 | 修改後 |
| :--- | :--- | :--- |
| `StoreBuff` | `INSERT INTO` | **`REPLACE INTO`** |
| `SaveBuff` | 直接逐筆存 | **先 `deleteBuff(pc.getId())` 清舊資料** |

備份：`CharBuffTable.java.codex-backup-20261024-BUFF-DUP.bak`

### 驗證

- JDK 8 編譯通過
- jar 熱替換成功
- 清除歷史髒資料（`DELETE FROM character_buff WHERE char_obj_id=536871476`）
- **實機登入成功且無「状态保存错误」**
