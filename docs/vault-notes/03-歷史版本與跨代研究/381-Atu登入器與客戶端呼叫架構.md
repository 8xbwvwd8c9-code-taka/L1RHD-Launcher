# 381 Atu 登入器與客戶端呼叫架構技術報告

> [!NOTE]
> 本架構基於 Atu-381-Launcher 系列（0918 / 1007 / 1015），由外層引導程序 `launcher.exe`、DirectX / GDI 鉤子注入動態函式庫 `present.dll`、WebView2 內嵌介面，以及客戶端二進位執行期修補（Binary Patching Gate）組成。

## 2. 突破上限原子防護機制 (Gate Barrier)

在 1015 版本登入器中，針對 **血魔上限突破** (`hp_mp_break`) 與 **防禦/魔防突破** (`ac_mr_break`) 引入了**全有全無 (All-or-Nothing)** 的原子修補機制：

### 2.1 為什麼需要防護閘？
- 過去只要「大部分位點」修補成功就放行遊戲，但只要有任何一個位點對不上（例如客戶端版本不一致、被其他修改器改過），會導致伺服端送出的寬格式封包與客戶端解碼錯位，數值錯亂甚至引發客戶端崩潰。
- **全新防護機制**：
  1. 連線放行前開啟短暫暫停視窗（約 `0.07 ~ 0.08` 秒）。
  2. 逐一比對每個修補位點的原始原廠位元組。
  3. **只要有任何 1 個位點不符，登入器絕不寫入任何位元組**，直接中斷遊戲啟動並彈出警告，要求玩家回傳 `launcher_debug.log`。
  4. 寧可明確失敗，絕不讓玩家帶著數值錯亂進入遊戲。

## 3. 畫面繪製與實體分類優化

### 3.1 別人隨從名字隱藏修正
- **問題根因**：
  遊戲對怪物類實體有「主人名」規則。當隨從（娃娃、寵物、召喚怪）的主人非玩家自身時，客戶端底層實體分類函式會將其**分類為玩家 (`Player`)**，導致繪製層替所有別人的娃娃頂部繪製出名稱，造成畫面擁擠混亂。
- **修復規則**：
  在 `present.dll` 的繪製管線中加入二次篩選：只要實體擁有主人名稱、且非真實玩家角色，一律抑制名稱文字繪製。真玩家與玩家自己的隨從則維持原樣渲染。

### 3.2 日誌降噪與靜默機制
- **封包失敗與缺道具解耦**：
  磨刀石、魔法寶石等消耗品不足屬於正常遊戲狀態。舊版登入器將「背包無道具」誤判為「封包發送失敗」，連續觸發多次後將前情傾印洗滿整個 `launcher_debug.log`。
- **現代機制**：
  背包缺道具一律靜默處理；只有在 Winsock 送出真的遭遇底層 Socket Error 時，才記錄單次失敗。
