# 🧩 815 登入器 list.txt 格式與「遠端清單」突破紀錄

> **狀態**：PASS（實機畫面已出現自訂伺服器 `88`，可點擊連線 `127.0.0.1:2000`）

## 1. 結論先講

1. `LineageM.exe` **不讀** `Encoder.ini`，只讀 `./list.txt`；而 `./list.txt` 只是**第三順位**。
2. 真正的第一順位是 **`0x0042DA20` 內向硬編碼遠端 URL 下載清單**，寫入 `%TEMP%\list_<n>.txt` 與 `%TEMP%\list_000.txt` 後才交給 `0x00430090` 解析。
3. 因此「改 IP 不生效」「列表被換回別人的服」「列表空白」都是同一條鏈上的不同斷點。

| 順位 | 來源 | 備註 |
|---|---|---|
| 1 | 硬編碼遠端 URL（`DAT_0069F542`，`.data` 檔內為加密態，僅記憶體明文） | 成功即採用，本機設定完全被忽略 |
| 2 | `./list.txt`（工作目錄） | 需先讓第 1 順位失敗 |
| 3 | `%TEMP%\list_000.txt` | 上一次的快取 |

## 2. 加密與 213-byte 記錄佈局（已證實）

### 2.1 加密鏈

```text
ServerDataN = base64( AES-128-ECB_Encrypt( key[:16], plain XOR ks ) )
ks[i]       = fixed[i] ^ key[i % 16]        # fixed = 客戶端 0x0041F7F4 起的 256 bytes
key         = "L1mTwsEc8RYi8Gcas"           # 客戶端 0x0063C250 硬編碼常數，AES 只取前 16 bytes
記錄長度    = 0xD5 (213)                     # 客戶端只解 ceil(213/16)=14 block，尾端 5 bytes 不可用
```

### 2.2 記錄佈局

| 偏移 | 長度 | 語意 | 實機樣本 |
|---|---|---|---|
| `+0x00` | 64 | **伺服器顯示名稱（UTF-16LE）** | `5E 79 ED 8A` = 神諭；`2C 6E 66 8A 3A 4F 0D 67 68 56` = 測試伺服器 |
| `+0x40` | 32 | **連線主機（ANSI）**，可主機名或 IP | `example.getmyip.com` / `114.32.x.x` |
| `+0x60` | 4 | 端口（dword, LE） | 9201 / 2001 |
| `+0x64` | 1 | 固定 `1` | 1 |
| `+0x65` | 16 | 備用 IP（可空） | 空 |
| `+0x75` | 1 | 樣本固定 `0` | 0 |
| `+0x76` | 1 | 輔助程式 (helper) | 1 |
| `+0x77` | 1 | 封包加密 (encrypt) | 1 |
| `+0x78` | 32 | 變身檔，**UTF-16LE 且帶 `./` 前綴** | `./lm210211.pak` |
| `+0xB8` | 1 | randkey | 0 |
| `+0xBD` | 4 | 清單全域值 | `0x01ED8E4E` |
| `+0xC1` | 4 | 清單全域值 | `0x0154F7CE` |

`[update]` 段：`ver` 是**登入器版本號**（實機清單為 `1001`），不是客戶端版本字串；`url` 是登入器自我更新下載點。

## 3. 四個坑與解法

### ❌ 坑 1：Encoder.exe 產出的 ServerData 客戶端解不開

- **現象**：用 `880登陸器\Encoder.exe`「生成列表」，`list.txt` 確實更新，但客戶端解出高熵亂碼。
- **根因**：`Encoder.exe` 對應的是**另一個客戶端 build**（`880登陸器\Lin.bin2` 7,012,976 bytes ≠ `G:\L815\Lin.bin2` 7,033,968 bytes），內建金鑰與 815 客戶端不同；UI 的「通訊金鑰」欄位不影響輸出（`WM_SETTEXT` 改前改後密文完全相同），值來自程式內建。
- **解法**：不走 GUI，直接依 [[#2. 加密與 213-byte 記錄佈局（已證實）]] 自行生成。工具：`G:\L815\_ghidra_scripts\make_list.py`。
- **附帶坑**：該 UI 是 `#32770` 皮膚容器，真實控件在**內層** `#32770`，`GetDlgItem` 抓不到（需遞迴 `EnumChildWindows` 比對 `GetDlgCtrlID`）；`BM_CLICK` 對「生成列表」會阻塞在 modal loop；實體點擊受 DPI 150% 與前景鎖影響，容易打到別的程序。

### ❌ 坑 2：改了 `list.txt` 完全沒效果，畫面仍是別人的服

- **現象**：`list.txt` 內容正確、時間戳更新，登入器照樣顯示遠端伺服器。
- **根因**：`0x0042DA20` 先下載清單，成功就完全不看本機檔案。
- **解法**：把 `0x0042DAAF` 的 `call 0x409CAF`（→ `FUN_0042CF10` 下載）改成「回傳失敗」，強制走 `./list.txt` 分支。

```asm
; 原始
0x0042DAAF  call 0x409CAF         ; E8 FB C1 FD FF
; 修補後（檔案位移 0x02CEAF）
0x0042DAAF  xor  eax, eax         ; 31 C0
0x0042DAB1  add  esp, 0xC         ; 83 C4 0C
0x0042DAB4  mov  [ebp-0x24], eax  ; 原本就在
```

- **工具**：`G:\L815\_ghidra_scripts\patch_lineagem_local_list.py`（含 `--revert`）。

### ❌ 坑 3：修補後一啟動就跳 `Run-Time Check Failure #0 - ESP was not properly saved`

- **現象**：MSVC Debug 執行期檢查視窗，登入器無法使用。
- **根因**：`FUN_0042CF10` 是 `__thiscall`，結尾為 `ret 0xC`（`0x0042D51C`）——**由 callee 彈 3 個參數**。只把 `call` 換成 `xor eax,eax`（5 bytes 用 nop 補滿）等於沒有人彈那 12 bytes，`__RTC_CheckEsp` 立刻判定 ESP 歪掉。
- **解法**：補丁必須是 `xor eax,eax; add esp,0xC`（2 + 3 = 5 bytes，剛好等長）。
- **判別通則**：改 `call` 前先看被呼叫函式結尾是 `ret` 還是 `ret imm16`；`ret N` 表示 callee 清棧，覆蓋掉呼叫就必須自己補 `add esp,N`。

### ❌ 坑 4：清單「空白」但能進遊戲

- **現象**：無錯誤視窗、左側伺服器列表空白，按「開始遊戲」仍可啟動。
- **根因**：`0x004328C0` 填列表時是 `CDuiString::Assign(記錄 + 0xbf0 + i*0xD5, -1)` —— 直接把**記錄開頭**當寬字串塞進 `btn_server1..8`。早期把 `+0x00` 當「未知 4 bytes」填 0，等於名稱是空字串。
- **解法**：`+0x00`（64 bytes）寫入 **UTF-16LE 顯示名稱**。
- **教訓**：`+0x00` 那 4 bytes 在樣本裡「看起來像雜湊」（`5E79ED8A` / `2C6E668A`），其實是 `神` `諭` 兩個中文字的 Unicode 碼位（U+795E / U+8AED）——**中文 UTF-16 很容易被誤判成隨機資料**。

## 8. 診斷紀錄：「用戶端版本配合錯誤」（2026-10-22）

> 狀態：**【已定位根因，未修復】**。此問題不是設定錯誤，而是**協議代次不相容**，381 核心無法靠補丁支援 815 客戶端。

### 8.1 現象

伺服器成功啟動（2000~2004 Listening）、登入器清單正常顯示、客戶端成功連上 2000 後：

```text
WARN - 初始連接次數: 1
客戶端 連線遊戲伺服器 服務端口:(2000) 127.0.0.1
[FIRST-PACKET] SEND ip=127.0.0.1 len=18 seed=1881492746 auth=false
[FIRST-PACKET] KEYS_READY ip=127.0.0.1
客戶端 離線: (127.0.0.1) 完成連線中斷!!
```

客戶端畫面（闇夜殺戮者書頁背景）彈出 `Lineage` 對話框：

> **用戶端版本配合錯誤。請重新下載用戶端程式。**

客戶端**一個包都沒回送**就斷線 → 它在收到首包的當下就判定版本不符。

### 8.2 根本原因：兩邊不是同一代協議

| 比較項 | 381 核心（`I:\Atu-381TO815`） | 815 客戶端（`G:\L815`） |
|---|---|---|
| 握手方向 | **伺服器先送** 18-byte 首包 | **客戶端先送** protobuf `CS_CLIENT_VERSION_INFO` |
| 首包 opcode | `0x96`（`S_OPCODE_INITOPCODE = 150`） | 客戶端 opcode 表中**不存在 0x96** |
| 版本交換 | `S_ServerVersion`：opcode `0x8B` + 5 個 dword | `SC_SERVER_VERSION_INFO`：protobuf message |
| 版本檢查點 | `S_OPCODE_SERVERVERSION = 139 (0x8B)` | `0x93 S_VERSION_CHECK`（0x8B 是 `S_EXCHANGEABLE_SPELL_LIST`） |
| 序列化 | 固定長度二進位 + Blowfish | protobuf（內嵌 runtime） |
| 世代 | L1J 3.81（約 2013） | NCSoft 8.x（2017-05-10 build） |

### 8.3 三項硬證據

**證據 1 — 客戶端映像內含完整 protobuf runtime**

**證據 2 — 伺服器首包 opcode 在客戶端 opcode 表中缺席**

客戶端 S_ opcode 名稱表位於 `FUN_00A269B0`（VA `0x00A269B0`）：
`0x8F S_MERCENARYSELECT`、`0x91 S_MOVE_OBJECT`、`0x92 S_PERSONAL_SHOP_LIST`、`0x93 S_VERSION_CHECK`、`0x95 S_REQUEST_SUMMON`、`0x98 S_NOTICE`、`0x99 S_EFFECT_LOC`、`0x9A S_PUT_OBJECT`、`0x9B S_WAR`、`0x9C S_VOICE_CHAT`、`0x9D S_KICK`、`0x9E S_DECREE`。

→ **跳過了 0x94、0x96、0x97**。而伺服器 `OpcodesServer.S_OPCODE_INITOPCODE = 150 = 0x96`，首包 `_firstPacket[2]` 正是 `0x96`。

**證據 3 — 同一編號在兩邊指向不同封包**

```java
// 客戶端 FUN_00A269B0
case 0x8b:  s_S_EXCHANGEABLE_SPELL_LIST     // 可兌換法術列表
case 0x93:  s_S_VERSION_CHECK               // 版本檢查

// 伺服器 OpcodesServer
S_OPCODE_SERVERVERSION   = 139;  // = 0x8B，版本包
S_OPCODE_INITOPCODE      = 150;  // = 0x96，首包
S_OPCODE_CHARLIST        = 93;   // = 0x5D
```

伺服器把 `0x8B` 當版本包，客戶端把 `0x8B` 當法術列表；客戶端的版本檢查在 `0x93`。整個 opcode 體系錯位。


- `UseLegacyLogin` / `WriteLegacyIpIni` 出自自製 C# `850Launcher.exe`（字串表可見 `IniDocument`、`LauncherConfig`、`ServerIp`、`ServerPort`、`UseLegacyLogin`、`WriteLegacyIpIni`），作用是寫出 `ip.ini`（內容 `127.0.0.1` / `2000`）。
- **`LoginWithoutUI.exe` 不是協議工具**：67,584 bytes 的 .NET 程式，字串為 `Lin.bin2`、`127.0.0.1`、`2130706433`（= `0x7F000001`）、`Wait Lineage Process Loading....MainWindowHandle=`、`GetTickCount`、`user32.dll`、`WaitForSingleObject` → 它是**等待遊戲視窗出現後自動填帳密並點擊登入**的 UI 自動化工具，繞過的不是協議，只是登入畫面。

### 8.7 可選路線

| 路線 | 內容 | 評估 |
|---|---|---|
| **A. 換 L1JTW8.5 核心** | 用同為 protobuf 世代的 8.5 核心取代 381 核心，重配資料庫與 `list.txt` | 唯一有機會真正登入成功的路 |
